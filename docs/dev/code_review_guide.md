# コードレビューガイド

## 1. はじめに

コードレビューは、実装されたコードを別の開発者の視点から確認し、**品質の向上・知識の共有・学習**につなげるための活動です。

**最初から完璧なレビューをする必要はありません。**

まずは自分が理解できる範囲でコードを確認し、気になる点があれば質問しましょう。必ずしも問題点を指摘する必要はありません。

レビューの経験を積みながら、少しずつ確認できる観点を増やしていきましょう。

ただし、実装の正しさや安全性に関わる重要な疑問点を未解決のまま承認しないようにします。

## 2. レビューの進め方

### ① PRの目的を理解する

PRの概要・関連Issue・受入条件（AC）を確認し、何を実現するための変更なのか理解します。

また、PRのマージ先（baseブランチ）が正しいか確認します。

### ② 変更されたコードを読む

GitHubの「Files changed」から変更差分を確認します。

PRの「レビュー観点」に記載された箇所を重点的に確認し、必要に応じて関連する既存のコードも読みましょう。

疑問点や改善点があればコメントを残します。

### ③ テストとCIの結果を確認する

変更内容に対応するテストが適切に書かれているか確認します。

また、GitHub Actionsで実行されるRSpec・RuboCop・Brakeman・Bundler-audit・Importmap-auditの結果も確認しましょう。

CIが成功していても、実装に問題がないことや、必要なテストが十分に書かれていることまで保証されるわけではありません。

### ④ 必要に応じて動作確認する

基本的にはコードレビューを中心としますが、必要に応じてローカル環境で実際にアプリを動かして確認します。

特に、画面の表示やTurbo・Stimulusによる操作が変更された場合などは、動作確認が役立ちます。

PRの「確認方法」や「スクリーンショット」も参考にしましょう。

### ⑤ レビュー結果を提出する

確認が終わったら、GitHubの「Submit review」からレビュー結果を提出します。

レビュー結果の選び方は第4章を参照してください。

## 3. レビューで確認する観点

まずは、以下の3つを意識しましょう。

### ① 要件を満たしているか

- Issueの要件・受入条件を満たしているか。
- 必要な処理が不足していないか。
- Issueと関係のない変更が含まれていないか。

**具体例**

Issueに「投稿を編集できること」という受入条件がある場合、投稿の編集フォームだけでなく、変更内容を保存する処理まで実装されているか確認します。

### ② コードに問題や疑問点がないか

- 意図したとおりに処理されるか。
- エラーが発生した場合も考慮されているか。
- 変数やメソッドの名前は分かりやすいか。
- 不必要に複雑な実装になっていないか。

**具体例**

投稿の作成機能を追加した場合、正常に保存できるだけでなく、タイトルが未入力のときには保存されず、適切にエラーが表示される実装になっているか確認します。

### ③ テストが適切か

- 変更した機能に対応するテストがあるか。
- 重要な正常系・異常系がテストされているか。
- テストの期待値が適切か。

**具体例**

投稿の削除機能を追加した場合、投稿者本人が削除できることに加え、他のユーザーが削除できないこともテストされているか確認します。

### 変更内容に応じて確認すること

慣れてきたら、次のような観点も意識しましょう。

- **セキュリティ**：認証・認可が適切か。例えば、他人の投稿を勝手に編集できないか。
- **データベース**：関連付けやDB制約は適切か。不要なクエリが発生していないか。
- **Railsの設計**：ControllerやModelの責務は適切か。Railsの仕組みを活用できているか。
- **Hotwire**：Turbo・Stimulusによる更新やイベント処理が適切か。

これらは重要度の低い項目という意味ではありません。変更内容に関係する場合は、優先的に確認する必要があります。

自分で判断できない箇所は、実装者や他のメンバーに質問・相談しましょう。

## 4. レビューコメントと承認

### コメントの種類

レビューコメントでは、指摘の意図が伝わるように次の3種類を区別します。

| 種類 | 意味 |
|---|---|
| **必須** | マージ前に解消する必要がある問題 |
| **質問** | 実装意図や処理について確認したいこと |
| **提案** | 必須ではないが検討してほしい改善案 |

**コメント例**

**【必須】** 他のユーザーの投稿も削除できる可能性があります。ログインユーザーの投稿だけを対象にする必要があると思います。

**【質問】** この処理をControllerに記述した理由はありますか？

**【提案】** この処理を別メソッドに分けると、読みやすくなりそうです。

修正を求める際は、理由もあわせて伝えましょう。

また、自分の好みと異なるだけの実装について、無理に修正を求める必要はありません。

### レビュー結果の選び方

| 結果 | 判断基準 |
|---|---|
| **Approve** | 重要な問題や未解決の疑問点がなく、承認できる場合 |
| **Comment** | 質問や意見を伝え、回答や追加確認を待ちたい場合 |
| **Request changes** | マージ前に修正が必要な問題がある場合 |

コードのすべてを完全に理解する必要はありませんが、重要な疑問点が残っている場合は無理にApproveしないようにしましょう。

また、軽微な改善提案については、必ずしも修正を求める必要はありません。

## 5. レビュー用チェックリスト

レビュー時に以下の項目を確認しましょう。

### PR・Issueの確認

- [ ] PRの概要と関連Issueを確認した
- [ ] Issueの受入条件（AC）を確認した
- [ ] PRのマージ先（baseブランチ）が正しいことを確認した

### コード・テストの確認

- [ ] 変更差分を一通り確認した
- [ ] 要件・正確性・可読性・テストの観点から確認した
- [ ] 変更内容に応じた重要な問題（セキュリティなど）を確認した
- [ ] 必要に応じて画面や機能の動作を確認した
- [ ] 必須のCIがすべて成功していることを確認した

### レビュー結果の確認

- [ ] 必須の修正事項や重要な疑問点が未解決のままになっていない
- [ ] Comment・Approve・Request changesを適切に選択した

### マージ前の確認（マージ担当者）

- [ ] 必須のCIが成功している
- [ ] 必要なレビュー承認を得ている
- [ ] 必須の修正事項が解消されている
- [ ] マージ先とマージ方法が正しい

---

**このチェックリストはレビューを補助するものです。**

チェックを付けること自体を目的とせず、気になる点があれば積極的に質問・相談しましょう。
